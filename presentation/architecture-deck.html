Trust Bank01 / 13
What this is

Not “the wallet, hardened.”
A platform three kinds of institutions run on.

01 · Banks & MFBs

Run their entire retail operation on it — accounts, ledger, loans, cards, statements, regulatory returns.

02 · BaaS resellers

Build products on top of it — issue accounts and move money without becoming a bank themselves.

03 · Every institution

Shares the platform (multi-tenant) or runs it alone (single-tenant), on the same code either way.

The ledger is never wrong, even when everything else fails.
What this is02 / 13
Guiding principles

The tie-breakers, in order.

What decides an implementation argument when two options both look reasonable.

01
Correctness over availability over latency
Fast and wrong is a lawsuit. Unavailable is a bad day.
02
The ledger is boring technology, on purpose
ACID, double-entry, SERIALIZABLE where money moves — no eventual consistency on balances.
03
Every action is idempotent and attributable
Idempotency keys on every mutation; every entry records who and why.
04
Segregation of duties is architectural
Enforced by separate credentials and maker-checker, not a policy document.
05
Compliance and fraud are first-class modules
In the transaction path where the regulator requires it; off it where not.
06
Tenant isolation is real, not assumed
Every table, every service, every event carries tenant_id — no exceptions.
07
Assume a dependency fails today
NIBSS, a card network, a data center — every one has a defined degraded mode.

Tenancy06 / 13
Security architecture

Defense in depth, mapped to what actually gets attacked.

Network & perimeter

  • Ledger and data stores in a private subnet, no direct internet route
  • Gateway/WAF is the only public surface; mTLS past it
  • Card PAN data in a separately segmented, PCI-scoped enclave

Identity & access

  • Least-privilege RBAC, mandatory MFA for staff
  • Maker-checker on every money- or limit-changing action
  • Tiered API keys — publishable vs. secret, per the AuthCore key spec

Secrets & cryptography

  • KMS/HSM for signing keys and PIN block encryption
  • TLS 1.2+ everywhere; mTLS internally
  • Automated, time-boxed secrets rotation

Application layer

  • Idempotency keys mandatory on every mutating endpoint
  • Per-tenant rate limiting — no noisy-neighbor spillover
  • Immutable audit log, separate from operational logs
Security07 / 13
High availability & disaster recovery

The transaction path's availability budget.

99.95%
target uptime for the transaction path — roughly 4.4 hours of downtime per year, budgeted, not aspirational.
  • Compute — stateless domain services, horizontally scaled, ≥2 availability zones
  • Database — synchronous replica for ledger writes within-region, async cross-region for DR
  • Event broker — durable, replicated; a "money moved" event is never lost to a node restart
  • Degraded mode is defined per dependency — e.g. NIBSS down means queue-and-retry, not platform failure
  • Circuit breakers and bulkheads between domains, so Cards being unhealthy can't take down Deposits
  • Chaos and game-day testing, on a recurring cadence, before this carries real institutional volume
HA & DR08 / 13
Consistency & transaction processing

How money moves without ever moving twice.

  • Inside the ledger — SERIALIZABLE isolation on every balance-affecting write; this is what prevents the double-spend/overdraft race
  • Across domains — saga pattern with compensating entries via the event outbox, not distributed two-phase commit
  • End-of-day processing — interest accrual and fee jobs are idempotent, safely re-runnable, and produce ledger entries like any other transaction
  • Reconciliation — continuous, automated, against every external settlement source; discrepancies raise to a review queue and are never silently auto-corrected
Consistency09 / 13
API & BaaS platform layer

What makes it a platform, not just a core.

  • Versioned REST API — OpenAPI-specified, documented deprecation policy from v1
  • Tiered keys — publishable/scoped for client-embeddable use, secret for server-side, both tenant-scoped and revocable
  • Signed webhooks — HMAC payloads, retry/backoff, and a replay history so partners can debug a miss
  • Sandbox with failure injection — simulate a NIBSS timeout or a KYC rejection, not just the happy path
  • Developer portal — docs, key management, usage dashboards; the product surface for a BaaS business
  • Per-tenant quotas — enforced at the gateway, independent of any other tenant's traffic

Phased rollout

“Everything a bank does” is the ambition — not the first milestone.

Ph.01
Deposits & wallets, hardened
Rebuild the proven ledger/idempotency/outbox patterns greenfield, with tenancy, HA, and security in from the start.
Ph.02
BaaS / API platform layer
Public API, tiered keys, sandbox, developer portal — turns the internal core into a resellable product.
Ph.03
Loans & credit
Highest-complexity domain — sequenced after the ledger and compliance plane are proven under real volume.
Ph.04
Cards issuing / switching
Deliberately last: longest external certification lead time, built on an already-audited ledger.
Ph.05
Regulatory automation & treasury
Full CBN/NDIC reporting and liquidity management, once real institutional volume is flowing.
